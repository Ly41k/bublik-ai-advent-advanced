Researcher: Файлы → независимое чтение заблокировано: действующие developer-инструкции запрещают чтение `/private/tmp`, где расположен runtime app. Пользовательское разрешение не расширяет этот доступ. Поэтому новые SHA256 и цитаты из исходников не представлены.

Связи → по переданному прошлому исследованию: `create_app → TaskService → TaskRepository → InMemoryTaskRepository`. Ниже это сведения из истории, а не заново проверенные факты.

Результаты исследования → в истории установлено, что TaskRepository задаёт `save(Task)` и `get(UUID)`, TaskService получает репозиторий через конструктор, а create_app создаёт конкретную реализацию. InMemoryTaskRepository хранит словарь в памяти. Его состояние существует в пределах экземпляра репозитория и процесса; после завершения процесса новый запуск создаёт пустое хранилище.

Архитектурный вывод: существующий порт позволяет заменить реализацию хранения, сохранив бизнес-операции сервиса. Composition root в main локализует выбор конкретного адаптера. Однако контракт отдельных save/get не обеспечивает атомарность всей последовательности чтение → изменение → сохранение.

Предложения для будущего перехода:

- Соединения: инфраструктурный SQLite-адаптер получает явно заданный постоянный файл; main создаёт адаптер и передаёт его сервису. Следует выбрать соединение на операцию либо управляемое соединение с определёнными правилами потокового доступа и закрытия. Конкретная стратегия пока не установлена.
- Транзакции: save заменяет полное значение задачи по UUID и возвращается после успешного commit; при сбое выполняется rollback. Ошибку чтения нельзя превращать в None, поскольку это означает отсутствие задачи. Защита от потерянных обновлений потребует отдельного решения о конкурентном доступе; один commit внутри save её не гарантирует.
- Перезапуск: предложенная проверка должна создать задачу, изменить статус, завершить первый процесс и прочитать тот же UUID из второго процесса через тот же файл БД. Проверяются все поля. Отдельно проверяются отсутствие записи после rollback и независимость разных файлов. Повторное открытие репозитория полезно, но само по себе не проверяет перезапуск процесса.

Выводы → границы порта и composition root дают место для замены хранения; долговечность дополнительно требует постоянного файла, согласованных транзакций и управления соединениями. Реализация SQLite не выполнялась.
