Связи → `create_app` — composition root: создаёт `InMemoryTaskRepository`, передаёт его в конструктор `TaskService` и сохраняет сервис в `app.state`. Сервис зависит от порта `TaskRepository`, а конкретный адаптер хранит значения `Task` в словаре. При обновлении сервис читает задачу, создаёт новое значение через `replace` и сохраняет его.

Результаты исследования → факты из прочитанного кода:

- `Task.__post_init__` преобразует статус через `TaskStatus(self.status)`: допустимые enum и строки «todo»/«done» нормализуются в TODO/DONE; недопустимые значения вызывают `InvalidTaskStatusError`. Проверенный enum записывается при инициализации frozen dataclass. `dataclasses.replace` создаёт новую Task с повторной инициализацией и проверкой.
- Это гарантия корректности доменного значения после успешного обычного создания. Она действует и при создании задачи вне сервиса; одной аннотации типа для такой проверки недостаточно.
- `InMemoryTaskRepository` сохраняет значения только в `dict[UUID, Task]`. Его `Lock` защищает отдельные чтения и записи; записи на диск и восстановления нет.
- Каждый вызов `create_app()` создаёт отдельный пустой репозиторий. Состояние принадлежит его экземпляру внутри процесса. После завершения процесса память теряется; следующий запуск начинает с пустого словаря. Новый экземпляр приложения даже в том же процессе получает отдельное хранилище.

Архитектурный вывод: инвариант отвечает на вопрос «допустимо ли значение статуса?», долговечность — «можно ли восстановить сохранённую задачу после завершения процесса?». Корректная Task может исчезнуть вместе с памятью. Постоянное хранилище, в свою очередь, требует проверки восстановленных значений: наличие записи на диске само по себе не обеспечивает доменный инвариант. Поэтому принятое исправление статуса и будущее постоянное хранение решают разные задачи.

Будущие предложения: SQLite-адаптер мог бы сохранить существующий контракт `save(Task) -> None` и `get(UUID) -> Task | None`: запись полного значения с заменой по UUID, чтение задачи и `None` только при её отсутствии. Сервис сохранил бы бизнес-операции и constructor injection; выбор конкретного адаптера остался бы в `main`. Восстановление через конструктор Task сохраняло бы проверку статуса. Ошибку чтения нельзя подменять отсутствием задачи.

Для долговечности потребовались бы постоянный файл БД, определённый жизненный цикл соединений и согласованная семантика commit/rollback. Это предложения, а не свойства нынешнего порта.

Открытый вопрос о транзакциях: должна ли вся операция `get → replace → save` быть атомарной относительно конкурирующих обновлений? Сейчас порт не задаёт общей транзакции, версий или условной записи. Даже атомарный UPSERT и commit внутри будущего `save` не охватывают предшествующее чтение. Если потребуется предотвращать потерянные обновления, понадобится отдельно согласовать гарантию и способ её выражения в контракте. Сам переход к SQLite этого решения не даёт.
