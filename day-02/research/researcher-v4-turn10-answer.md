Researcher: Файлы → `Task` проверяет допустимость статуса, а `InMemoryTaskRepository` определяет, сколько живут задачи. Поэтому исправление, которое объяснял Bug Fix Engineer, обеспечивает корректность значения, но не сохранность после перезапуска. Самостоятельно прочитала эти файлы, `create_app`, `TaskService`, `TaskRepository` и документацию; полные тексты с заголовками FILE и вычисленными SHA256 выведены успешной командой Python `-B -c`.

Связи → `create_app` — composition root: создаёт `InMemoryTaskRepository`, передаёт его в конструктор `TaskService` и сохраняет сервис в `app.state`. Сервис импортирует порт `TaskRepository`, а не конкретный адаптер. При изменении статуса он читает задачу, создаёт новое значение через `replace` и сохраняет его.

Результаты исследования → факт из текущего кода: `Task.__post_init__` выполняет `TaskStatus(self.status)`. Допустимые enum и строки «todo»/«done» становятся `TaskStatus.TODO`/`DONE`; недопустимые значения приводят к `InvalidTaskStatusError`. Проверенный статус записывается при инициализации frozen dataclass. `dataclasses.replace` создаёт новую Task и повторяет эту проверку. Таким образом, инвариант обеспечивается и при обычном создании задачи вне сервиса.

Хранение устроено отдельно: адаптер записывает Task в словарь своего экземпляра, защищая отдельные `save` и `get` блокировкой. Записи на диск и восстановления в нём нет. Каждый вызов `create_app()` создаёт новый пустой репозиторий. Пока используется прежний экземпляр, данные доступны; завершение процесса уничтожает память, а следующий запуск начинает с пустого словаря.

Архитектурный вывод: допустимый статус и долговечность — независимые гарантии. Корректная задача может исчезнуть вместе с памятью. Постоянная запись тоже сама по себе не гарантирует корректность восстановленного доменного значения.

Будущее предложение: SQLite-адаптер мог бы сохранить существующий контракт `save(Task) -> None` и `get(UUID) -> Task | None`: сохранение полного значения с заменой по UUID, возврат задачи либо `None` при отсутствии. Бизнес-операции и constructor injection остались бы в сервисе, выбор адаптера — в `main`. Восстановление через конструктор Task сохраняло бы доменную проверку; ошибку хранения нельзя выдавать за отсутствие задачи.

Открытый вопрос о транзакциях: требуется ли атомарность всей последовательности `get → replace → save` относительно конкурентных обновлений? Сейчас порт её не обещает, а Lock охватывает только отдельные операции. Даже commit атомарной записи в будущем адаптере не защитит предшествующее чтение от устаревания. Если нужна защита от потерянных обновлений, потребуется отдельно согласовать гарантию и её выражение в контракте.

Выводы → порт уже отделяет бизнес-операции от способа хранения. Для будущей долговечности дополнительно понадобятся постоянный файл, управление соединениями и определённые правила commit/rollback. Предлагаемая проверка — запись в одном процессе и восстановление всех полей в другом через тот же файл; она здесь не выполнялась.
